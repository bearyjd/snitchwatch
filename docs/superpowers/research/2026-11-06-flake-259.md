# Flake #259: `bridge_runtime::silent_answer_tests` counts too high

Date: 2026-11-06. First seen on origin/main d9e6a3d6, re-checked against 727130b4. Status: fixed by this PR (lib test binary; see "Side effect" for the integration binaries).

## Cause

`analysis_export_controller::tests::stale_delivery_and_off_qt_save_keep_independent_lifetimes`
(src/analysis_export_controller/tests.rs, test fn at ~:83, `#[test]` before the fix at :68) loads
`tests/probes/analysis_export_lifecycle_probe.qml`, which instantiates the
production `qml/main.qml`. `main.qml:250` calls
`settingsController.refreshPreferences()`, which spawns a thread that runs
`crate::learned::attach(&learned_path())` (src/settings_controller.rs, `attach` at ~:348 after the fix, `discard_stale` at ~:347; the fix wraps both).

That call attaches a real `FileBackend` (default
`~/.config/snitchwatch/learned.json`) to the process-global recorder in the lib
test binary, and starts its `learned-writer` thread. From then on:

- every `learned::set_active(true)` queues a `Load`, and the writer merges the
  stored list into the fresh window's totals (src/learned.rs:53-58,
  shared.rs `do_load`);
- every `set_active(false)` flushes that window's rows to the file.

So each learning window in `silent_answer_tests` inherits the previous windows'
rows (2, 4, 6 ... in CI, where the file starts empty). That matches the issue:
`left: 4 / right: 2` and `left: 6`. The attach runs on a thread with no
`TEST_LOCK`, so the failure depends on the analysis test running before or
during the silent tests.

Evidence:
- A backtrace written from `learned::attach` shows
  `SettingsController::refresh_preferences::{closure}` as the caller. Run alone,
  only the analysis test produces it (`delegate_incubation` and
  `analysis_export_native` have no tests).
- Deterministic repro, 3/3 failing:
  `QT_QPA_PLATFORM=offscreen QT_QUICK_CONTROLS_STYLE=Basic <lib test bin> analysis_export_controller bridge_runtime::silent_answer_tests --test-threads=1`
  fails `a_lag_marks_the_record_incomplete...` (`left: 102/104/106, right: 2`;
  the number grows by 2 per run because the real file keeps accumulating) and
  then `a_lag_outside_a_window_marks_nothing` (cascade: the panic skipped
  `end_learning()`, leaving the window open). The same
  silent_answer_tests alone: 14 passed.
- stderr from the attach is invisible in the test log because that test
  redirects fd 2 (`common::capture_stderr`).

Every module-only run passes because the analysis test is not in the filter.

analysis test happened to finish before the learning windows started or the
file was empty; it is an ordering race, not load sensitivity.

## Static candidates (writers of process-global state without `TEST_LOCK`)

1. **Proven culprit.** src/settings_controller.rs `learned::attach` (~:348 now)
   via `refresh_preferences` (main.qml:250), reached from
   src/analysis_export_controller/tests.rs:68-90. Also runs
   `discard_stale` (~:347, can delete the real file) and
   `settings_learning::startup` (reads and may write the real settings file).
2. src/silent_mode.rs:519-526 (`NEEDS_RULE` cap test) and
   src/connections_model/tests.rs:222 call `mark_needs_rule` without the lock.
   The cap test pushes 4105 ids and evicts others' marks, so a concurrent
   `needs_rule(...)` assertion in silent_answer_tests could fail. Different
   symptom (assert on a mark, not a count); not observed.
3. Ruled out: `spawn_sweep` (silent_mode.rs:312) only runs on the test's own
   runtime and is cancelled on drop; the recorder writer thread only exists
   once something attaches (candidate 1); no test CODE calls `set_state`,
   `set_active`, `answer_*` or `record` directly outside the locked modules
   (but see candidate 4 for the indirect writers) (learned/facade_tests.rs and silent_answer_tests.rs take
   `TEST_LOCK`); the global bridge runtime (`ensure_started`) is only started
   from `tests/*.rs` binaries, which are separate processes.
4. Indirect writers (found in review): loading the production main.qml also
   runs `AlertHost.qml:46` -> `bridge_feed.rs` `set_state(Off)` and, via the
   preferences push, `apply_preferences` -> `set_active(false)`. Unlocked, the
   analysis test could flip the silent mode or end the window under a
   silent_answer test that is mid-window.

## Fix

- `settings_controller.rs` `refresh_preferences`: under `cfg!(test)` it takes
  the demo-mode branch (no `discard_stale`, no `learned::attach`, no
  `settings_learning::startup`), so the lib test binary never points the
  process-wide recorder at a file or starts `learned-writer`. The
  `tests/*.rs` binaries link the non-test lib and are unaffected.
- `silent_mode.rs` (`needs_rule_is_remembered_and_bounded`) and
  `connections_model/tests.rs` (`a_silently_answered_row_needs_a_rule...`) now
  take `learned::TEST_LOCK`: they write the process-wide `NEEDS_RULE`
  registry that `silent_answer_tests` asserts on.
- Guard: `analysis_export_controller` test asserts
  `!learned::has_backend()` (test-only accessor) after the production
  main.qml ran, so any future attach from a lib test fails right there.

Failing first, on a fresh throwaway HOME (so counts are the CI ones):

    H=$(mktemp -d); mkdir -p $H/.config $H/.state $H/.data $H/run; chmod 700 $H/run
    HOME=$H XDG_CONFIG_HOME=$H/.config XDG_STATE_HOME=$H/.state XDG_DATA_HOME=$H/.data \
    XDG_RUNTIME_DIR=$H/run QT_QPA_PLATFORM=offscreen QT_QUICK_CONTROLS_STYLE=Basic \
    timeout 120 <lib test bin> analysis_export_controller \
      bridge_runtime::silent_answer_tests --test-threads=1

Before the fix: the guard fails, plus `an_allow_is_recorded_once_after_it_was_sent`
(`left: 4, right: 2`), `the_start_of_learning_records_rows_already_allowed...`
(`left: 4, right: 2`) and `a_send_that_failed...` (`left: 10, right: 8`), 2 of 2
runs. After: 15 passed, 2 of 2 runs.

## Side effect on dev machines

Before this fix, every run of the whole lib test binary on a dev machine read
and rewrote the real `~/.config/snitchwatch/learned.json` (and ran
`discard_stale` / the settings startup against the real config dir), because
the analysis test loaded the production main.qml. On the machine used for this
investigation the stored `/usr/bin/curl` count was inflated by roughly 80
connections. Lib tests now skip that path entirely; the investigation's own
later runs used a throwaway `HOME`/`XDG_*`, and the real files' mtimes were
unchanged across them. The inflated file is not repaired here (owner's call).
The `tests/*.rs` binaries link the non-test lib, so they run the production
startup in-process. Isolation for them is a constructor in
`tests/common/mod.rs` (`.init_array`, Linux only, so it runs before `main`
while the process is single-threaded, so the isolation itself never calls
`set_var` after test threads exist).
It creates `/tmp/snitchwatch-probe-home-XXXXXX` (or `$TMPDIR/...`) with
`mkdtemp`, creates `.config`, `.state`, `.data` and `run` with mode 0700
(chmod and stat-verified, else the process exits), exports `HOME` and
`XDG_{CONFIG,STATE,DATA}_HOME` / `XDG_RUNTIME_DIR` to them, defaults the three
`QT_*` variables, records the original HOME in
`SNITCHWATCH_PROBE_ORIGINAL_HOME` and removes the directory at exit
(`atexit`). The exit hook deletes only the path this process created (kept
in a static, with the creator pid; a fork-without-exec child deletes
nothing) and never trusts the env var. Every `setenv` is checked, and an
empty or relative `TMPDIR` is treated as unset. It uses libc calls on stack
buffers plus one small `Vec` and one leaked `CString` for the directory name.
A binary gets it by declaring `mod common;`.

Who is covered, exactly: `tests/harness_isolation_guard.rs` scans
`tests/*.rs` and `tests/*/main.rs` and requires an uncommented `mod common;`
line (a commented, block-commented or quoted one does not count) in every file
that contains any of these markers: `QQmlApplicationEngine`, `QQmlEngine`,
`QGuiApplication`, `QApplication`, `probe_runner`, `SettingsController`,
`learned::`, `ensure_started`, `bridge_runtime::`, `TestLink`, `BridgeConfig`.
Allowlisted, with reasons in the guard: `qml_source_guards.rs` (text scans) and
`live_loop.rs` / `rule_hits_live.rs` (these two DO start a bridge, via
`snitchwatch_bridge_cli::run`, but with an explicit tempdir `BridgeConfig`, so
they touch neither `~/.config/snitchwatch` nor the runtime dir). The other
files without `mod common;` are source-scan guards and pure-logic tests that
match no marker. The guard failed first listing nine files (`smoke`,
`wizard_qml`, `blocklists_model_qml`, `connections_model_qml`,
`connections_page_diagnostics_qml`, `profiles_model_qml`, `rules_model_qml`,
`rules_page_diagnostics_qml`, `traffic_model_qml`), and, when widened to
`QApplication`, `application_widgets.rs`; all now declare it. A test that
reaches app code by a route none of the markers name is not seen by the guard,
so the claim is exactly: no test file that mentions those markers runs against
`~/.config/snitchwatch`. The lib-binary isolation additionally depends on
`src/analysis_export_controller/tests.rs` being compiled into the lib test
build (it is the only lib test that includes `tests/common/mod.rs`). A
hand-run `cargo run` of the app intentionally still uses the real config.

`XDG_CACHE_HOME` is not redirected: a cold cache is slow, and the timing
could not be separated from host load (load average 70+ during the runs), so
it is left alone; caches live outside `~/.config/snitchwatch`.

## Residual risk and status of the last verification (round 3 and later)

The constructor runs from `.init_array`, so no `set_var` is needed for the
isolation itself and none races test threads. Other `set_var` calls remain in
test code: the `is_none`-guarded `QT_*` defaults in `init_headless_qt_env()`
(no-ops after the constructor) and per-test calls in `drawer_keyboard_qml.rs`,
`learning_end_qml.rs`, `analysis_export_qml.rs`,
`gui_diagnostics_snapshot_qml.rs` and others (`grep -l set_var tests/*.rs`);
those run after test threads exist and are the residual race (they point at
tempdirs; the isolation does not depend on them). The remaining exposure is a binary that does not declare `mod common;` and starts no QML
engine (not covered by the guard), and non-Linux hosts, where the constructor
is compiled out and `home_isolation()` panics with a clear message.

Verification state: on the heavily loaded host (load average 70-85) the full
integration run (`cargo test -p snitchwatch-kirigami --tests`) timed out once
after 8 binaries and once failed in `answer_surfaces_keyboard_qml` ("cannot Tab
to the banner's Deny"), a focus-traversal probe. It is load-sensitive, not a
constructor effect: at load average 10-16 the committed constructor harness
passed that probe 10 of 10 (orchestrator) and 6 of 6 (executor). Also verified
on a throwaway home: the isolation guard test, the deterministic ordering
command (16 passed), and the whole lib binary at `--test-threads=1` and `8`
(1625 passed, 0 failed, 3 ignored). The real `~/.config/snitchwatch/learned.json`
and `settings.json` modification times were unchanged by all of these runs. The
complete integration run on an unloaded host is left to CI (the `kirigami` job
runs `cargo test -p snitchwatch-kirigami` headless).
