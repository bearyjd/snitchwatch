# r16 group B: "No longer recommended" orphan list (#113)

Branch `r16/B`, from main 5b4813a. Deferred from r15-D (see its #113 section).

## Problem

A daemon rule under the reserved `snitchwatch-default-` prefix can outlive its
curated entry with no saved copy. The plan only auto-deletes a no-longer-offered
rule that is Snitchwatch's recorded, unedited copy, the Recommended page lists
only current entries, and the Rules page refuses every command under the prefix.
The user then has no way to remove it.

## Design

- **Orphan (pure, `curated/orphans.rs`).** A name is an orphan when all hold:
  1. it is in the live rule list (not `left_out`);
  2. its id is a valid curated id (`valid_id`), so `CuratedCommand::delete` can be built;
  3. no current entry has that id;
  4. `!choices.was_installed(id)`: neither a recorded copy (`installed`) nor an
     `installed_ids` record. A recorded copy belongs to the existing plan.
- **Wire.** `SetCuratedDefaults.orphans: Vec<CuratedOrphanSummary>`, skipped when
  empty, default on read. An older GUI ignores the field; an older bridge never
  sends it, so a new GUI shows no section and no button. No capability needed.
  The summary carries `id`, `enabled`, `fileLeft` (skipped when false) and an
  optional fixed-text `problem`. No daemon-sourced rule content is sent.
- **Removal.** New `ClientMessage::RemoveCuratedOrphan { id }`. The existing
  `RemoveCuratedDefault` (entries only) is unchanged. The ask is refused (nothing
  queued) when the bridge is inert, the id is invalid, a current entry, or
  recorded. Otherwise it is queued and the worker woken (`requests += 1`).
- **Send-time re-check (`manager_orphans.rs`).** In the reconcile pass, each
  queued orphan is re-checked against the live cache and the current choices,
  with the state guard held through queue admission (as an install does; lock
  order state, then cache). If it is no longer an orphan, nothing is sent and a
  warning is logged; the next list shows the truth. A changed daemon stream
  re-queues the rest; an unknown list or an inert bridge clears them.
- **Feedback.** `OK`: gone from the list. Daemon `ERROR`: the daemon dropped it
  from memory but its file may remain, so the row stays (`fileLeft`, no Remove)
  until the daemon reconnects. Any other failure: the row shows the fixed
  problem text while it stays an orphan on the same daemon stream. Busy (not
  queued) is re-queued, as the edited-copy Remove does.
- **Kirigami.** New `curated_orphans.rs` (Qt-free store logic), `orphansJson` and
  `removeOrphan(id)` on `CuratedDefaultsModel`, and a "No longer recommended"
  section as the ListView footer: name, fixed status, problem, Remove... ->
  confirmation -> Remove rule / Cancel, matching the edited-copy Remove.
- **Rules page.** The reserved-prefix delete guard stays as it is; removal goes
  only through this curated path.

## Conservative choices (open in the sketch)

- **Disabled orphan:** listed, with fixed text saying it is turned off on the
  Rules page, and removable the same way. Hiding it would leave it stuck again.
- **Inert bridge:** sends no orphans. Its choices may be unknown (unreadable
  file) or absent (per-user bridge), so "no saved copy" can't be told.
- **Refused delete:** shown until the daemon reconnects only (in memory, not
  saved); a reloaded file lists the rule again as an orphan.

## Known gaps (not fixed here)

- A recorded but **edited** no-longer-offered copy: not an orphan (recorded), and
  the plan won't delete an edited copy. Still stuck.
- A `left_out` name (too large to read) under the prefix with no entry: not listed.
- An id that fails `valid_id`: cannot be deleted through the curated command, so
  not listed.

## Tests

- Unit: orphan detection, each conjunct (current entry, recorded copy,
  `installed_ids`, invalid id, non-prefix, left_out, missing).
- Manager: re-check at send time (no longer an orphan -> nothing sent), refused
  ask (entry / recorded / inert), refused delete -> fileLeft, failure -> problem.
- Round trip (`bridge-cli/tests/curated_orphans.rs`, real bridge + mock daemon):
  Rules-page delete refused; RemoveCuratedOrphan -> one DELETE_RULE, list empties;
  entry id sends nothing; stuck file -> fileLeft.
- Kirigami: store unit tests and a QML probe of the section.
- Mutants: re-check forced true, each detection conjunct, prefix guard, inert check.

## Results

Done. Mutants (private copy, all killed): send-time re-check forced true; each
detection conjunct dropped (listed, left_out, entry, recorded, valid id);
`was_installed` narrowed to `installed`; `is_reserved_curated_name` forced false
(the Rules-page delete in the round trip reaches the daemon); the removal path's
inert checks dropped. `manager.rs` grows by 6 lines (806 -> 812, already over the
800 cap before this; the orphan logic lives in `manager_orphans.rs`).

## Review round (#181)

- LOW-1: the orphan delete goes through the guarded dispatch (`Guard::Present`):
  queued only on the daemon stream whose list decided it, while that list still
  has the name; a HELLO in between re-queues it for the follow-up pass. The
  edited-copy Remove (`manager.rs` `remove`) is left as it was: switching it is
  one call, but a HELLO would then become a sticky "isn't connected" failure
  instead of a re-queue, so it needs its own change.
- LOW-2: a request is queued only for an id the cached list shows as an orphan.
- LOW-3: asking again keeps a "file may remain" note until a reconnect.
- `manager.rs` is under the cap again: the live re-checks moved to
  `manager_checks.rs` (pure move; the bridge test list is identical, 1534 tests).
