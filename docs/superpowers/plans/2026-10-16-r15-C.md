## #55 collapse repeated event rows

A Qt-free `RowCollapse` rewrites each connection `ServerMessage` before the
row store and the group tree see it (both apply sites: `apply_now` and
`flush_grouped_messages`, after stale-session messages are dropped).

- **Who collapses.** Only daemon event rows (id `event-…`, or
  `<session>:event-…` once qualified) that are decided (`action` set) and
  not `deferred`. Pending rows and Ask rows (`ask-…`) are never absorbed and
  never absorb anything, so a prompt can't be hidden inside a collapsed row.
- **Key.** Raw `action` string (not `Verdict`, so two unknown actions never
  merge), `decided_by_default`, `matched_rule`, `auto_answer`, `process`,
  `process_path`, `dst_host`, `dst_ip`, `dst_port`, `protocol`,
  `direction`. Stricter than the owner's list: it can only merge less.
- **Window.** `COLLAPSE_WINDOW_MS = 10_000`: a row joins the latest
  representative of its key when its start is within 10 s of that
  representative's last-seen time (a sliding window, so a burst of SYN
  retransmits stays one row while it keeps coming). Otherwise it becomes a
  new representative.
- **Shape.** The representative keeps its id, its row and its place (row
  identity and the selection survive). Absorbing a row becomes an
  `UpdateConnectionRows` of the representative, so Qt sees `dataChanged`,
  never an insert. Two new roles: `repeatCount` (1 when not collapsed) and
  `lastSeenMs`. The delegate shows "×N · last seen hh:mm:ss" when N > 1.
- **Messages for absorbed ids.** `Remove` of a member drops it (count goes
  down, representative updated). `Remove` of a representative with members
  promotes the oldest member (remove + insert; the selection on that row
  is lost, which only happens if the bridge withdraws an event row: today
  it only withdraws pending rows). `Move` of a member moves its
  representative. `Update` of a member whose key still matches is kept as
  the member's row; one whose key changed is released as its own row. An
  `Update` that changes a representative's key releases all its members.
  `Clear` resets everything.
- **"From now".** Turning on the since-filter seals every open window, so a
  row after the cut starts a new representative and is not hidden inside
  one that started before it. The representative keeps its first-seen
  `started_at_ms` (inspector, prefill and filter unchanged).
- **Grouped mode.** Header totals now count a collapsed row once.
- **Exports.** The GUI has no connection export (only rules import/export),
  and the bridge cache/history is untouched, so exports are unchanged.
- **Trimming.** The GUI store is never trimmed; the bridge evicts silently
  without telling GUIs, so the only removals are withdrawn pending rows
  (never collapse members) and `Clear`.

## #114.3 remembered-answer twin rows

Decided 2026-10-16 (team-lead): option (a), a GUI heuristic that FOLDS
the twin (counted, never hidden). Exact pairing is not possible in the GUI:
`ConnectionRow` carries no pid or source port.

- In `RowCollapse`: a decided Ask row whose `matched_rule` is a bridge
  answer name (`is_answer_name`) waits for one twin. The first decided
  event with the same whole `CollapseKey` (same action, the answer's own
  rule name, same program, host, IP, port, protocol, direction) starting
  within `TWIN_WINDOW_MS` (`ANSWER_TIMEOUT` + `COLLAPSE_WINDOW_MS`) of the
  Ask's start folds into the Ask row: its `repeatCount` and `lastSeenMs`
  update. At most one event per Ask row.
- If the real twin never comes, the app's next connection under that rule
  is the one folded: counted, never lost, never across verdicts (tested).
- An update that changes the Ask row's key releases the folded event.
- Asks past twice their window are forgotten (memory bound).
- **Future bridge work (option b, out of scope for r15):** put pid and
  source port on the wire, or drop the twin event in the bridge as #102
  does for once answers, for an exact pairing.

## #146 every dismissed pending row

- `ConnectionsPage.qml`: `dismissedIds` (an array used as a set) replaces
  `dismissedId`. `dismissInspector` adds the closed row; `runAuto` prunes ids
  that are no longer pending (`isPendingRow` is false for unknown ids, so
  withdrawn and old-session ids go too); both `runAuto` and
  `selectOldestPending` pass the whole set.
- `oldestPendingRowIndex(exceptIdsJson)`: a JSON array of ids (the crate's
  existing pattern for lists across the QML boundary; a malformed value is
  treated as no exceptions).
- **Tie-break (one rule).** Equal `started_at_ms`: the earlier row in the
  store (arrival order) wins, the rule `alert_row.rs` already uses (it has no
  projection to use). The inspector used "topmost visible", which differs in
  grouped mode (store A, B, C; projection A, C, B). Both now use store order,
  so the alert and the inspector pick the same row.

## PR #167 review, round 1

Fixed (TDD, mutants):
- `seal()` also forgets waiting Asks, so a connection after "From now"
  never folds into an Ask row from before the cut.
- Memory: `expire(at)` (at most once per 10 s of event time) drops open
  rows whose window ended (alone ones entirely) and Asks past twice their
  twin window; absorbed rows keep only id and start (rebuilt from the
  representative's row when released or promoted). A flood test bounds the
  state to the flows of the last two windows.
- One Remove naming a representative and its repeat (either order) no
  longer re-inserts or re-upserts either.
- A deferred Ask row never waits for a twin.
- The "×N · last seen" note leads the host line, so a long host's middle
  elision never hides it.

Noted, no change (they merge less or only affect display):
- Released or promoted rows are appended at the newest end of the list.
- An out-of-order old event can displace the open representative (the
  next repeat then starts a new row).
- `takes()` accepts a row up to 10 s before a representative's first
  occurrence, so a pre-cut event can count into a post-cut row's ×N.
- `dismissedIds` is not cleared on a session change; harmless because ids
  are session-qualified (`qualify_connection_ids`).
