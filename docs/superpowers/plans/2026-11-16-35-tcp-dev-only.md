# #35: TCP gRPC only behind a dev flag; per-user Unix socket by default; user unit dropped

Issue #35. Owner decision 2026-11-15: keep the TCP gRPC fallback, but only behind a dev-only
flag. Default and packaged paths must never listen on TCP. Owner answers 2026-11-16:
1. Without the flag, the bridge falls back to a per-user Unix socket. It does not refuse to start.
2. The per-user systemd unit is dropped. system-bridge is the only shipped flavour.
3. The bluebuild recipe's daemon config adopts `unix:opensnitchd.sock`.
4. The flag also gates the embedded dev flow (Tauri/Kirigami).
5. The spike crate is in scope.

Branch `feat/35-tcp-dev-only`. There are three PRs, so each one reviews and reverts alone.
PR A goes first; B and C depend only on A's flag name.

## Flag: `SNITCHWATCH_DEV_TCP=1` (env only)

The CLI is env-only by design (`cli.rs:1-5`: unknown arguments are ignored), so the flag is an
env var, not a CLI switch. Its parsing mirrors `SNITCHWATCH_SYSTEM_BRIDGE` (`main.rs:89-93`):
- Unset: no TCP anywhere (bridge-cli, Tauri, spike).
- `=1`: TCP is allowed. The bridge binds `SNITCHWATCH_GRPC_BIND` (default `127.0.0.1:0`). The
  address must be loopback (`ip.is_loopback()`); anything else, including `0.0.0.0`, is an
  error. The existing #35 warning stays, reworded to name the flag.
- Any other value: hard error before any I/O (no socket, no token file).
- `SNITCHWATCH_GRPC_BIND` set **without** the flag is a hard error that names the flag. It is
  not ignored: a stale unit or script that pins `:50051` would otherwise fall back silently to
  the Unix default while its daemon dials TCP.
- The flag together with `SNITCHWATCH_SYSTEM_BRIDGE=1` is an error. System mode never has TCP.

The name says TCP rather than gRPC on purpose: in PR C it also gates Tauri's TCP webview proxy.

Env resolution is a **pure function** over `Option<OsString>` inputs (the `cli.rs` pattern).
It returns `GrpcListen` or an error and is unit-tested without touching the process
environment. No test calls `std::env::set_var`: it is process-global, races parallel tests,
and is `unsafe` in edition 2024.

## Per-user Unix socket (default without the flag)

- **Path:** `$XDG_RUNTIME_DIR/snitchwatch-grpc/opensnitchd.sock`. This is a **sibling** of the
  WS directory, not inside it: the Flatpak is granted all of `xdg-run/snitchwatch`
  (`org.snitchwatch.Snitchwatch.yml:71`). A sandboxed GUI running as the same uid would pass
  any uid check and could pose as the daemon. The basename matches the system socket
  (`/run/snitchwatch/opensnitchd.sock`).
- **No `XDG_RUNTIME_DIR`:** refuse to start with a clear error. Do not use
  `auth::runtime_dir()`'s `temp_dir()/snitchwatch` fallback (`auth.rs:89-94`); a shared `/tmp`
  path is the squatting problem again.
- **Directory:** create it at 0700, then `lstat` it. It must be a real directory (not a
  symlink), owned by `geteuid()`, with mode exactly 0700; otherwise refuse. Remove a stale
  socket only after that check, as `ws_server.rs:119-128` does. Then bind and `chmod 0600`.
  The 0700 directory covers the window between bind and chmod.
- **Peer policy:** a new `OwnerUnixIncoming`, next to `RootUnixIncoming`
  (`activation.rs:139-163`), with the same bounded accept loop. It accepts peers whose uid is
  0 (opensnitchd) or the bridge's own euid (dev tools, tests) and rejects every other uid with
  a warning. The same uid is not a boundary on Linux: that process could ptrace or replace the
  bridge anyway.
- **Transport:** this endpoint is `GrpcEndpoint::Unix(path)`, so it gets
  `DaemonTransport::Unix` semantics (`lib.rs:225-228`). That has three effects, stated in the
  PR:
  - commands go to the current stream only (`daemon_commands.rs:57-59`);
  - rule-hit counters are trusted (`cache/rule_hits_handle.rs:247-248`);
  - blocklist leftover handling takes the Unix branch (`blocklists/leftover.rs:75`).

  This is acceptable because only root and the same uid can connect. A new `UnixUser` variant
  was considered and rejected: no behaviour would differ.
- **#34 caveat:** binding replaces a running bridge's gRPC socket, exactly as it already
  replaces the WS socket and token. That is unchanged; the doc comment says so.
- **stdout:** prints `GRPC_SOCKET_PATH=<path>`, the line system mode already uses
  (`main.rs:106-108`). `GRPC_LISTEN_ADDR=` is printed only in dev-TCP mode.

### Daemon-address implication

opensnitchd has **one system-wide** `Server.Address`, so it cannot dial a per-uid path in
general. An operator could hand-set `unix:///run/user/<uid>/snitchwatch-grpc/opensnitchd.sock`.
Root bypasses the 0700 DAC, but the absolute `unix:///` form is unverified on 1.8.0
(`docs/packaging/system-bridge-integration.md:148-155`), and nothing ships that config. So the
per-user Unix default has **no packaged consumer**: it is a dev/test default that never
listens on TCP. That is consistent with answer (2): the per-user unit could not be made to
work without a per-uid daemon address, so it is dropped rather than migrated. Docs must say
plainly that a desktop install uses the system bridge.

## PR A: `feat/35-tcp-dev-only` (bridge-cli gate, per-user socket)

1. **Type the listener.** In `config.rs`, replace `grpc_bind: SocketAddr` with
   `grpc_listen: GrpcListen { DevTcp(SocketAddr), UserUnix(PathBuf) }`. Add the pure resolver
   `resolve_grpc_listen(dev_flag, grpc_bind, xdg_runtime_dir, system_flag)`. `from_env` only
   reads the env and calls it. Drop the dummy at `lib.rs:142`: `run_system` builds its
   endpoint without a `BridgeConfig` gRPC field, or uses a system-only constructor.
2. **The gate is in the library, not only in `from_env`.** `run`, `run_with_answer_timeout`
   and `run_with_options` match on `grpc_listen`: `DevTcp` goes to `run_tcp`, `UserUnix` goes
   to a new `run_user_unix` (directory checks, bind, `OwnerUnixIncoming`). An in-process
   embedder therefore can only get TCP by naming `GrpcListen::DevTcp`. Tauri cannot bypass the
   flag by building a struct literal.
3. **One test-support constructor.** `BridgeConfig::dev_tcp_for_tests(ws_socket_path)`
   (`#[doc(hidden)] pub`) returns `DevTcp(127.0.0.1:0)`. One mechanical commit rewrites the
   `grpc_bind: "127.0.0.1:0".parse()…` literals in the default-member test files above to use
   it, so existing semantics (TCP, `DaemonTransport::Tcp` fan-out) are untouched. The
   Kirigami tests get the same edit but are built explicitly (below). Every test that spawns a
   bridge keeps or gains an isolated `XDG_RUNTIME_DIR` tempdir (CLAUDE.md, issue #34).
4. **Text.** Update `--help` (`cli.rs:53-95`), the `main.rs` module doc, the run_tcp warning
   and `diagnostics/mod.rs:60`. Keep the literal `SNITCHWATCH_SYSTEM_BRIDGE=1` (stage.sh greps
   it) and `SNITCHWATCH_GRPC_BIND` (`bridge_artifact.py:1134` greps it, until PR B changes
   that check).
5. **Tests first (RED, then GREEN):**
   - Resolver unit tests (pure): unset gives `UserUnix` under `snitchwatch-grpc`; `=1` gives

     the flag; flag plus `SYSTEM_BRIDGE=1` is an error; no `XDG_RUNTIME_DIR` without the flag
     is an error.
   - Directory checks: a symlinked directory, a directory with the wrong mode, and a directory

## Security considerations

- Default and packaged paths: no TCP listener anywhere. This is enforced by type (`GrpcListen`)
  and by shape tests on `packaging/`.
- The dev flag cannot reach beyond loopback. `0.0.0.0` is refused in both the bridge and the
  spike.
- The per-user socket sits outside the Flatpak-granted directory and refuses `/tmp`.
  Directory ownership and mode are checked with `lstat` before any unlink or bind. Peers must
  be uid 0 or the same uid.
- A stale `SNITCHWATCH_GRPC_BIND` fails loudly rather than degrading silently.
- Image without the overlay: the daemon has no UI and applies `allow`. This is no regression
  against squatting; the prompt function is lost, which was already the case once nothing
  ships the user unit.
- The system flavour is untouched: `run_system`, `RootUnixIncoming` and the activation paths
  change only by losing the dummy TCP field.

## Risks

- Large mechanical test diff (about 40 files). Keep it in its own commit with no behaviour
  change, so review can skim it.
- Kirigami tests are not in default-members and their CI job is best-effort. Run them locally
  or they rot.
- The release tarball's layout changes and the repro pins must be refreshed. A draft
  `release.yml` run will show any drift.
- A tower or operator host that still has an enabled user unit from an older install will
  fail to start (the `GRPC_BIND` error) after upgrade. That is intended; the error and
  `RUNBOOK.md` say what to remove.
- `DaemonTransport::Unix` semantics on a same-uid socket: a same-uid fake daemon can become
  the current stream. This is accepted under the same-uid rule above, and the PR states it.
