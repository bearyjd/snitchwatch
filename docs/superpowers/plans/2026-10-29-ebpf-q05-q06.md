# Q05/Q06: eBPF host proof and comparable proc-vs-eBPF measurement (preparation)

Status: **preparation only, 2026-10-29.** Nothing here was run on a host. This PR
adds this plan and `scripts/ebpf/measure.py` (read-only sampler plus an

`../specs/2026-10-24-competitive-feature-roadmap.md` (Q04/Q05/Q06, "Dual-mode

## Goal
Produce the evidence the roadmap asks for before any image change: (1) the
three modules, root and kernel checks pass on the owner's host; (2) short-lived
process attribution is correct; (3) the GUI stays correct when eBPF is not
ready; (4) a comparable full-day CPU/RSS comparison of `proc` vs eBPF, reported
with the unknown-process rate. A measured result that disproves the performance
hypothesis is kept (roadmap line 245-246).

## Known vs unknown
Known (from the repo, `ebpf-groundwork.md`, read from the vendored v1.8.0 tree):
- The daemon looks for `opensnitch.o` (required), `opensnitch-procs.o`,
  `opensnitch-dns.o` in `/usr/local/lib/opensnitchd/ebpf`, then
  `/usr/lib/opensnitchd/ebpf`, then deprecated `/etc/opensnitchd`.
- If the main module fails it falls back to `/proc` itself (log: "Process
  monitor method /proc"). If only `opensnitch-procs.o` is missing it logs
  "Process monitor method ebpf" and runs the `/proc` monitors alongside. A log
  saying "ebpf" alone does not prove all three loaded.
- The modules are not CO-RE; they need headers matching the running kernel.
- The image builds opensnitchd from Go source and installs no `.o` files, so
  eBPF has nothing to load today (per tower, 2026-10-22).
- Both shipped configs say `ProcMonitorMethod: ebpf`
  (`packaging/system/opensnitchd-default-config.json:21`); the tower overrides
  it to `proc` after staging.
- One reference only: opensnitchd on `proc` averaged ~20.5% of a core over
  12.6 h, RSS 122 MB at 6 min to 222 MB (r16 plan, "Evidence from the r14
  laptop").
- GUI side (Q04, implemented): the process-monitor mode is the constant "not
  reported by opensnitchd"; `/proc` is never a health error.

Unknown (do not assume):
- Whether the v1.8.0 RPM's prebuilt modules load on kernel 7.2 and attribute
  correctly; whether `kernel-devel` for the custom Bazzite kernel exists.
- Any eBPF CPU/RSS figure; whether eBPF lowers unknown-process rows.
- Whether the Bazzite kernel has FTRACE_SYSCALLS, debugfs/tracefs, lockdown
  restrictions.
- The exact BPF program names to expect in `bpftool` output (not read from
  source here).

## Owner checklist (read-only; the owner runs all of it)
Run on the host as the owner. Commands marked **ROOT** need `sudo`; the agent
that wrote this plan did not and will not run them. None of these changes
config, loads a module or restarts a unit. Save the output of each.

1. Identity. `uname -r`; `rpm-ostree status | head -20`;
   `systemctl show opensnitchd -p ActiveState,MainPID,ExecStart --no-pager`.
   Expect a kernel string, the booted image digest, `ActiveState=active`, a
   nonzero PID. Record all three (they go in every run record). If ExecStart
   contains `-process-monitor-method`, that CLI flag overrides the config file;
   note which.
2. Configured method (intent, not actual).
   `grep -n ProcMonitorMethod /etc/opensnitchd/default-config.json`. Expect
   `"ProcMonitorMethod": "proc"` or `"ebpf"`. Interpret: configured intent
   only; the tower may overwrite `ebpf` to `proc`.
3. Module files. `ls -l /usr/local/lib/opensnitchd/ebpf /usr/lib/opensnitchd/ebpf
   /etc/opensnitchd/*.o 2>&1`. Expect either "No such file" everywhere (today's
   image: eBPF cannot load) or exactly `opensnitch.o`, `opensnitch-procs.o`,
   `opensnitch-dns.o` in one directory. Flag any `.o` in `/etc/opensnitchd`
   (stale copies can be picked up) and any of the three missing.
4. Kernel options. `zcat /proc/config.gz 2>/dev/null | grep -E
   '^CONFIG_(BPF|BPF_SYSCALL|BPF_EVENTS|KPROBES|KPROBE_EVENTS|CGROUP_BPF|FTRACE_SYSCALLS)='`
   (fallback: `grep ... /boot/config-$(uname -r)`). Expect `=y` for all seven.
   Any missing line blocks the process module; report it.
5. Kernel headers, only needed if modules must be built in the image:
   `ls -d /usr/src/kernels/$(uname -r) 2>&1; rpm -q kernel-devel`. Expect the
   directory and a version equal to `uname -r`; a mismatch or "not installed"
   means the build route (plan step 2 in the r16 plan) is blocked, and prebuilt
   modules are the only route.
6. Filesystems and policy. `findmnt -t debugfs,tracefs`;
   `cat /proc/sys/kernel/unprivileged_bpf_disabled`;
   `cat /sys/kernel/security/lockdown 2>&1`; `mokutil --sb-state 2>&1`.
   Expect debugfs and/or tracefs mounted (the procs module needs it), a `0`,
   `1` or `2` for the sysctl (informational; opensnitchd runs as root), and a
   lockdown line such as `[none] integrity confidentiality`. `integrity` or
   `confidentiality` selected is a known obstacle for kprobes: report it, do
   not change it. `lockdown` and some `/sys/kernel/debug` reads can need
   **ROOT**.
7. **ROOT** Daemon log, the decisive check (read-only):
   `sudo grep -E '\[eBPF|Process monitor method|opensnitch-procs|unable to load' /var/log/opensnitchd.log | tail -40`.
   Which lines count as evidence (vendored v1.8.0): the module loader tries
   every search directory and logs `[eBPF] module specs error` / `module
   collection error` per failed directory, then `continue`s
   (`daemon/core/ebpf.go:42-57`); the same loader serves `opensnitch.o`,
   `opensnitch-procs.o` (`procmon/ebpf/events.go:96`) and `opensnitch-dns.o`
   (`dns/ebpfhook.go:118`), and the lines do not name the module. So those
   lines alone never identify which module failed or whether the load later
   succeeded in another directory.
   - Ready candidate: `[eBPF] module loaded: <dir>/opensnitch.o`, `.../opensnitch-procs.o`
     (and `.../opensnitch-dns.o`; DNS failure only warns) AND "Process monitor
     method ebpf" (`procmon/monitor/init.go:96`) with NO `opensnitch-procs.o not
     available:` line. The `module loaded:` line does include the path, so use
     it to name each module. Necessary, not sufficient (steps 9-10).
   - Procs module failed (documented line): `Process monitor method ebpf`
     followed by `opensnitch-procs.o not available: ...`
     (`init.go:105-106`). The daemon stays on ebpf and runs the `/proc`
     monitors alongside; not full eBPF attribution.
   - Fallback to `/proc` (documented lines): `unable to load eBPF module
     (opensnitch.o)...` from the loader (`core/ebpf.go:60-64`; the name in
     parentheses identifies the module) AND a later `Process monitor method
     /proc` (`init.go:132`).
   - Everything else is **inconclusive**, not fallback: `module specs error` or
     `module collection error` without one of the lines above (a later
     directory may have loaded it, or it was the DNS module), a lone `Process
     monitor method /proc` with no eBPF error lines (eBPF may simply not have
     been requested), missing log lines. Report the raw lines; do not infer.
8. **ROOT** Kernel messages: `sudo dmesg | grep -i -E 'bpf|verifier|lockdown' | tail -30`.
   Expect nothing alarming on a clean load. Verifier or lockdown lines at the
   daemon start time explain a fallback.
9. **ROOT** Program ownership (read-only). `bpftool prog show` is system-wide
   (systemd, other tools also load programs), so a program listed does not
   prove opensnitchd owns it. Get the daemon pid from step 1, then:
   `sudo bpftool prog show --json | python3 -c 'import json,sys; p=int(sys.argv[1]);
   [print(x["id"],x.get("name"),x.get("type"),x.get("pids")) for x in json.load(sys.stdin)
   if any(q.get("pid")==p for q in x.get("pids",[]))]' <opensnitchd-pid>`
   (the `pids` field needs a bpftool built with skeleton support; if it is
   absent, use `sudo sh -c 'ls -l /proc/<pid>/fd | grep -c bpf-prog'` and
   `sudo sh -c 'grep -c prog_id /proc/<pid>/fdinfo/*'` as coarser ownership
   evidence; the glob must expand inside the privileged shell, because the
   owner's own shell cannot read that directory and would pass a literal `*`).
   Then classify what the daemon owns, because two independent things attach
   programs:
   - **Process-monitor programs** (follow `ProcMonitorMethod: ebpf`): from
     `opensnitch.o`, kprobes/kretprobes on `tcp_v4_connect`, `tcp_v6_connect`,
     `udp_sendmsg`, `udpv6_sendmsg`, `udp_tunnel6_xmit_skb`,
     `inet_dgram_connect`, `iptunnel_xmit`
     (`ebpf_prog/opensnitch.c:134-546`); from `opensnitch-procs.o`,
     tracepoints `sched_process_exit`, `sys_enter/exit_execve`,
     `sys_enter/exit_execveat` (`ebpf_prog/opensnitch-procs.c:66-169`).
   - **DNS programs** (NOT tied to the process-monitor setting): uprobes on
     libc `gethostbyname` and `getaddrinfo` from `opensnitch-dns.o`
     (`ebpf_prog/opensnitch-dns.c:94,151,173`). The daemon starts this listener
     separately (`daemon/main.go:650-663`), so it can be present on a `/proc`
     run and is not evidence of eBPF process monitoring.
   `bpftool prog show` reports uprobes and kprobes under the same type
   (`kprobe`), and program names are UNVERIFIED (they come from the C function
   names, not read here). So classify by attach point:
   `sudo bpftool perf show` lists each attachment as kprobe/kretprobe with a
   kernel function, `tracepoint` with a name, or uprobe with a file path and
   offset; match its `prog_id` against the ids printed above.
   Success is ownership-based and per class. eBPF run: daemon-owned
   process-monitor programs (kprobes on the functions above and the exec/exit
   tracepoints) are present. `/proc` baseline: daemon-owned process-monitor
   programs are ABSENT; daemon-owned DNS uprobes are allowed and are recorded,
   not rejected. Report what appears; programs owned by other pids are
   irrelevant.
Steps 1-9 are observation-only. The attribution workload is deliberately NOT
part of this list: see "Active workload" below.

Stop and report if step 7 shows the documented procs-module-failed or fallback
lines; do not edit config to "fix" it.
Changing the monitor, shipping modules or flipping the tower verifiers is a
separate image PR through the tower's cut process (r16 plan), after this
evidence.

## Active workload (NOT read-only): short-lived process attribution
Run this only after steps 1-9, and only if the owner chooses to. It starts real
outbound connections from short-lived processes, so it **can raise Snitchwatch
prompts** and, if answered, create or change rules. Either do it on a test
host, or first create an explicit allow rule for the test destination (for
example `example.com:443` for `curl`) so no prompt appears, and delete that
rule afterwards. Do not let it run unattended with prompts enabled.
1. Pick the window: note the start and end UTC time.
2. Run the loop with curl reporting its own evidence, one line per request:
   `for i in $(seq 20); do curl -sS -m 5 -o /dev/null -w '%{time_starttransfer} %{remote_ip}:%{remote_port} %{http_code}\n' https://example.com; done | tee requests.txt`
   Count N = lines with a non-empty remote_ip (requests that actually made a
   connection). Failed or retried requests are visible there instead of being
   assumed. Note the proxy environment (`env | grep -i proxy`); with a proxy,
   the observed destination is the proxy.
3. Count observations from the supported evidence. The cache-summary export
   cannot be joined per connection: destinations and applications are
   per-export HMAC pseudonyms (`destinationRef`, `appRef`), and `appBasename`
   is disclosed only for allowlisted paths (`/usr/`, `/opt/`, `/app/`, `/bin/`,
   `/sbin/`); a curl outside those has no name. Comparable fields across
   exports are aggregates only: group `port`, `protocol`, `verdict`, `count`,
   first/last observed time, and `appBasename` when disclosed. So:
   - Use a quiet window on a test host (or keep other network apps closed) and
     export it twice for the same `[from, to)` UTC window: once unfiltered and
     once with the `missingPath` filter.
   - M = sum of `count` of groups with `port` 443 and `protocol` tcp in the
     unfiltered export (any program; this is why the window must be quiet).
     K = the same sum restricted to `appBasename == "curl"`. U = the same sum
     in the missing-path export. Compute these BY HAND (for example a short
     `python3 -I -c` over the two JSON files); `measure.py` has no subcommand
     for N, M, K or U, only the unknown-rate and sampler subcommands.
   - Per-connection attribution (which program each connection was attributed
     to) is not available from the export. Where a specific row is disputed,
     use the GUI connection list or the daemon connection log for that window
     as evidence, and cite it.
   Observations are cache rows; DNS lookups, retries and connection reuse make
   M differ from N, so report N, M, K and U with the window and the caveat.
4. Repeat on a fresh `/proc` run for the baseline with the same loop.
Measured ratios, not a fixed count (both computed by hand): attribution
ratio K/M, and coverage M/N. PROPOSED tolerance (owner decides): K/M >= 0.95 on eBPF and not below the
`/proc` run's K/M; M/N must be reported and, if below 0.9 on either run, the
run is inconclusive (the cache is missing observations) rather than a pass. The gap M - K - U (known to the export but not named curl) is reported and
inspected in the GUI; it is not assumed to be curl or not curl.

## Fallback test: GUI when eBPF is not ready
Requirement (roadmap 216-224): `/proc` is a supported backend, never a health
error; prompts, rules, history and export must not require eBPF; the GUI never
writes daemon configuration; unavailable data stays unavailable.
Evidence to collect on the host once per state (eBPF modules absent; eBPF
requested but fell back; eBPF active):
- Daemon Health page shows no "problem" summary caused only by the monitor
  method; the monitor line reads "Process monitor: not reported by
  opensnitchd" in all three states (it is a constant, never "proc"/"eBPF").
- Tray tooltip likewise; a prompt can still be answered; a rule still saves.
- Existing automated coverage (already merged, to be re-run, not rewritten):
  `daemon_health_model.rs` `unreported_monitor_method_allows_healthy_proc_or_ebpf`
  (an `EbpfSupport` Unknown with everything else Ok gives no problem), the
  `tray_health.rs` guard that tray/health text never names a mode, and the
  `diagnostics/mod.rs` tests for the daemon-alert path. Kirigami tests need Qt
  (`cargo test -p snitchwatch-kirigami`, headless env in `CLAUDE.md`).
Pass: all three states show the same neutral monitor line, no GUI error, and
the only health problem is one the daemon itself reported.

## Gaps found (not fixed here)
1. A daemon process-monitor alert marks `EbpfSupport` as `Failed`
   (`crates/snitchwatch-bridge/src/diagnostics/mod.rs:187-193`), which the GUI
   shows as a problem. On a host that requested eBPF, failed to load it and
   fell back to a working `/proc` monitor, v1.8.0 may emit such an alert
   (UNVERIFIED which text it sends). The GUI cannot tell "fell back and
   works" from "monitoring broken", so a supported fallback could read as a
   health error, contrary to the owner invariant. Owner decision: reword the
   alert as informational vs wait for an upstream "active method" field (Q04
   options B/C). Verify with the step 7 log and the Health page on a forced
   fallback; do not force one on the production host.
2. The cache-summary export cannot distinguish a missing process path from a
   path outside the disclosed allowlist by itself (`appBasename` is absent in
   both). The unknown-rate definition below therefore uses the export's
   `missingPath` application filter rather than inferring from the unfiltered
   file.
3. The export is a bounded, incomplete cache summary (`coverage.completeness`
   is always `incomplete`). The rate is over the cached window only, not
   all-day traffic, until history (r17) exists.

## Unknown-process rate
Definition. An observation is *unknown* when the bridge cache row has no
process path (absent or empty), which the export classifies as the
`missingPath` application identity. Rate = unknown observations / all
observations in the same UTC window, counted by group `count` (cache rows, not
sessions or bytes). A path that merely lacks an allowlisted prefix is known.
Compute (owner exports twice for the identical window, same requested
`[from, to)`):
```
python3 scripts/ebpf/measure.py unknown-rate \
  --total all.json --missing-path missing.json
```
`all.json` has no application filter; `missing.json` uses the `missingPath`
selector. The tool refuses mismatched windows, a non-filtered second file, a
second file that discloses names, any verdict filter, filters that differ
beyond the missing-path one, malformed counts, or unknown > total. It reports
`"truncated": true` plus a warning for every reported omission (`rowOmissions`,
unexamined rows, and `groupOmissions.groupLimit/artifactLimit/wireLimit`, or
unreadable coverage); a truncated rate is not over the full window and must not
be used for the gate. Report the rate per run and per fixed sub-window (for example per
hour) so a day-long comparison is not one number. Gate for Q05/Q06 (PROPOSED,
see below): eBPF unknown rate not higher than the `proc` run's, and the
active-workload attribution ratio acceptable (see "Active workload").

## Controlled workload for CPU/RSS (proc vs eBPF)
The repo states the gate (see Gates). It does not define the workload beyond
"fresh run A, comparable conditions, a normal workday" and "asks/min as a
context proxy" (measurement-series note). Proposed concretization (PROPOSED,
owner decides):
- Same host, same image digest, same kernel, same opensnitchd build, same rule
  set, same GUI state (open or closed for the entire run), same user schedule.
  Only `ProcMonitorMethod` differs. Run A (`proc`) then run B (`ebpf`), or
  interleave on alternate days; always a fresh daemon start for each.
- Duration >= 24 h each, started at the same wall-clock time, covering a
  normal workday; no updates, reboots or image changes during a run.
- Fixed daily routine, written down before run A, repeated in B: for example
  open the browser and a fixed list of sites, one package-manager metadata
  refresh, the active-workload loop at the start of each hour of the first
  3 h. The routine is the owner's; the plan only requires it to be identical.
- Sample every 60 s (matches the measurement-series note): 
  `python3 scripts/ebpf/measure.py sample --name opensnitchd --interval 60
  --duration 86400 --out <dir>/A-opensnitchd.csv`
  (refuses to overwrite an existing file or follow a symlink; `--force`
  overwrites a regular file only), and the same with
  `--name snitchwatch-bridge`. Run both in the background as the owner; the
  sampler needs no root (CPU/RSS/threads, load average and system fork rate are
  world-readable `/proc` files). It does not record fds or journal asks/min
  (those need root; optional, per the measurement-series note).
- Record per run: kernel, image digest, opensnitchd build, effective method
  (step 1/7 output), GUI state, start/end, the routine, any unusual events.
- Report (`measure.py summarize` per CSV): mean, median and p95 CPU; RSS start,
  end, peak and slope (MiB/h, least squares); fork rate and asks/min medians as
  context; the unknown-process rate per run.
Caveat: the script's CPU is delta of utime+stime over wall time as percent of
one core, so it can exceed 100 on multi-thread daemons; `summarize` assumes one
PID per name (stop and report if two sampled).

## Gates
Stated in the repo: ship eBPF only if a full day on eBPF has **lower mean CPU
than a fresh `proc` run under comparable conditions** (about 20.5% of a core is
a sanity reference only), **RSS slope no worse than `proc`**, **no daemon errors
or degraded state in the log**, correct process association, and the tested
`proc` fallback kept. Sources: `2026-10-22-r16-platform-upgrade.md:48-55`;
`../specs/2026-10-22-r16-measurement-series.md:51-57` ("r16 acceptance gate");
roadmap `2026-10-24-competitive-feature-roadmap.md:242-246` and `:269-270`
(also "report unknown-process rate").
Not stated anywhere: numeric thresholds (how much lower "lower" is; what
"no worse" tolerance applies to the slope; how many unknown rows fail
attribution; what counts as run-to-run noise). PROPOSED, not decided:
- Mean CPU of B below A by more than the A-vs-A day-to-day spread (one extra
  proc-only day gives that spread), else report "no measurable difference".
- RSS slope of B <= slope of A plus 10% of A's slope.
- Unknown rate of B <= A; active-workload K/M >= 0.95 and not below A's.
- Daemon log of B: zero `[eBPF]` error lines and no fallback line.
