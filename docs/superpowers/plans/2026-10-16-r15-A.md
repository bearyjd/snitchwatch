#### Tower / image changes for r15 (for the orchestrator to pass on; not done here)

1. Build the image with the system overlay: run
   `packaging/system/stage.sh <image-root> <verified bridge binary> <sha256>`
   in the image build and copy the staged tree in **after** the recipe's
   `files` module. It carries the daemon config (`unix:opensnitchd.sock`,
   `deny`), the `opensnitch.service` drop-in and the sockets as one artifact;
   the recipe's own config is TCP/`allow` and must be replaced by it.
2. Enable `snitchwatch-system-bridge-grpc.socket` and
   `snitchwatch-system-bridge-gui.socket` (preset or `systemctl enable` at
   image build time); never enable `snitchwatch-system-bridge.service`
   directly.
3. Do **not** install or enable the per-user `snitchwatch-bridge.service`;
   install the `org.snitchwatch.Snitchwatch.system.yml` Flatpak profile.
4. Desktop users: `usermod -aG snitchwatch-ui <user>`, new login session.
5. **Before rebooting into the image** (PR #166 M2, ostree's `/etc` merge
   keeps a locally edited config): `sudo ostree admin config-diff | grep
   opensnitchd` and `jq .Server.Address /etc/opensnitchd/default-config.json`.
   If config-diff lists `M etc/opensnitchd/default-config.json`, run `sudo cp
   /usr/etc/opensnitchd/default-config.json /etc/opensnitchd/` so the merge
   takes the new image's file; after the reboot the `jq` must print
   `"unix:opensnitchd.sock"` (otherwise repeat the `cp` and restart
   `opensnitch.service`). Details: system-bridge-integration.md.
6. Verify on the tower: the daemon connects via the relative address
   (`/var/log/opensnitchd.log`, bridge journal), `ss -xl` shows
   `/run/snitchwatch/opensnitchd.sock` root 0600, nothing listens on
   `127.0.0.1:50051`, and `sudo grep 'Error compiling list rule'
   /var/log/opensnitchd.log` is empty. Keep a console login handy: if the
   socket fails, the daemon still starts with `deny` (fail closed, PR #166
   M1); recovery steps are in system-bridge-integration.md.

#### PR #166 round 1 (security review + CI)

- **CI:** the `audit` job's checkout gets `submodules: true`, as the
  candidate contract requires of every CI checkout.
- **H1:** the `deny` + `unix:` config moved to
  `packaging/system/opensnitchd-default-config.json`, installed only by
  `stage.sh` with the drop-in and socket. The recipe's own copy is back on
  TCP, now with `allow`. Chosen over dropping it (the image would then get
  upstream's `allow` + `unix:///tmp/osui.sock`, a world-creatable path) and
  over making the recipe run `stage.sh` (it has no verified binary to stage).
  `deny` on the squattable TCP port protects nothing (a squatter can save a
  new `DefaultAction` via CHANGE_CONFIG) and risks a lockout, so `allow`.
  `packaging_shape.rs` fails if any `unix:` Server.Address ships outside
  `packaging/system/` or the recipe names one.
- **M1 (owner: fail closed):** the drop-in uses `Wants=` + `After=` and
  `WorkingDirectory=-/run/snitchwatch` (the `-` so a missing directory can't
  stop the daemon either). Socket-down detection stays in the docs: with its
  socket down the bridge isn't running, so neither it nor the GUI's
  four-check diagnostics can report it.
- **M2:** `/etc` merge check above and in the integration doc.
- **L1:** `StartLimitIntervalSec=0` on the system bridge service, so a crash
  loop keeps retrying (paced by `RestartSec=2s`) instead of leaving the
  bridge and its sockets failed; documented in the recovery section.

### 2. #109.1 amplification: moot for the system flavour, not fixed

On the system flavour the daemon connection is a root-only 0600 socket, so
no other local process can be a "fake daemon": the snapshots that trigger
reconciles all come from the real daemon. The amplification needs the TCP
user flavour, which is documented as not deny-safe and is out of the image.
A TCP-only fix (route bridge-built commands to one stream) is not a
one-liner (`DaemonCommands` TCP routing deliberately fans out), so skipped.

### 3. #109.3 space out `lists` rule deletes

`DaemonRuleSink::delete` waits `DELETE_SPACING` (1 s) between consecutive
deletes, never before the first and never after a `daemon_unavailable` stop,
so verdicts get the loader's lock between two ~4 s holds.
`with_delete_spacing` (tests set zero, like `with_timeout`). Test first with
paused time: two deletes are seen at least the spacing apart.

### 4. #115 account lookups (display path, `rules_sync`)

The #155 single-flight covers only the curated resolver. Here:
- **Single flight:** at most one blocking lookup batch at a time; uids
  wanted while one runs wait in a bounded queue the running batch drains.
  A drop guard clears "in flight" even on a panic.
- **Don't cache failures:** a uid with no name is retried after a cool-down
  (60 s) rather than remembered as `None` forever.
- **No wiping claims:** `learn()` evicts one finished entry when full instead
  of clearing the map; claims live outside it.
- **Bounded batch time:** a batch stops starting lookups after 5 s; the rest
  are released for a later snapshot.
- **Only the bounded snapshot:** an over-limit snapshot looks nothing up;
  rules over the size limits are skipped.
- **Late names honour `PublishHold`:** the late publish goes through
  `publish_after_command`'s hold-aware path.

### 5. #115 snapshot reordering

`Subscribe` takes an arrival ticket (`RulesSync::receive`, with the revision)
before any await; `stage` refuses to replace a same-key entry with a later
ticket. `snapshot.sequence` is the ticket: still unique per staged snapshot
(#162's curated epoch compares it for equality only).

### 6. #115 re-adoption journal

Each staged entry keeps a capped journal (256) of the changes confirmed,
refused (a refused delete removes the rule, tower r12) and prompt rules
remembered while the cache holds its snapshot. Adopting it
again (a second HELLO of the same key, or `readopt`) replays the journal on
top of the snapshot. Over the cap, `readopt` withdraws (as without a
journal) and a HELLO adopts the bare snapshot, with a warning.

### 7. cargo-audit CI (PR #33 decision)

New `audit` job in `ci.yml`: `cargo install --locked cargo-audit@0.22.2`
(same pin as `release.yml`), `cargo audit` with explicit `--ignore`s, each
with its reason in the workflow (not `.cargo/audit.toml`, which would also
hide them from `release.yml`'s shipped-crate gate):
- RUSTSEC-2026-0194 / RUSTSEC-2026-0195 (quick-xml 0.37.5 via
  `tauri-winrt-notification`, 0.38.4 via `plist`): Windows/macOS-only
  dependencies of the Tauri shell and notify-rust, never compiled on Linux
  (`cargo tree --target all` only); the fix needs quick-xml 0.41, an
  upstream semver bump.
- rustls 0.23.45 -> 0.23.46 in `Cargo.lock`: RUSTSEC-2026-0346 to 0349.
  rustls **is** compiled into the shipped bridge (reqwest's TLS for list
  downloads), so the next release's `audit-bridge` gate would have failed.
- quinn-proto 0.11.14 -> 0.11.19 (RUSTSEC-2026-0185, 0338 to 0342; the
  refreshed DB needs >= 0.11.18). Not compiled (reqwest's optional http3):
  `cargo tree -p snitchwatch-bridge-cli --no-default-features -i
  quinn-proto` (and `-i rand@0.10.3`, which the bump added to the lock) print
  nothing for the release target. No ignore.
- h2 is 0.4.19; RUSTSEC-2026-0258 is patched in `>= 0.4.16`. Nothing to do.
- Warnings (unsound/unmaintained) don't fail the job (no `--deny warnings`).
- The local run fetched the live advisory DB (no sandbox network limit
  here). The CI job fetches it too, so a new advisory turns PRs red until
  it is bumped or ignored with a reason: intended.

Residual, not fixed: a change confirmed between a new `Subscribe`'s arrival
and its *first* adoption is not replayed; the snapshot may already hold it,
so replaying it blindly could be wrong.

`DELETE_SPACING` callers: nothing wraps the sink's deletes in a timeout or
holds an async lock across them; an orphan purge or bulk unsubscribe of N
lists (two rules each) now takes about 2N s longer, in the background.
