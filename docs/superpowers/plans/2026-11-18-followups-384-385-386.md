## #384: the onboarding "Start daemon" action

### The issue's premise is stale

The issue (and the #379 plan, `2026-11-17-379-retire-tauri.md:31`) says
`crates/snitchwatch-kirigami/src/wizard.rs:27-32` runs
`systemctl --user start snitchwatch-opensnitchd.service`. That was true of the Tauri crate
(`commands.rs:85-98`, now deleted). The Kirigami code was changed in `1def7459`
("feat: add socket-activated system bridge deployment", 2026-10-04) and now runs:

- `wizard.rs:27-30` `start_unit_via_systemctl()` → `wizard.rs:32-45` `start_unit_with()`, which runs
  `systemctl --system start opensnitch.service`, via `which::which("systemctl")`.

No code starts the per-user unit any more. The action is still wrong, though, for these reasons:

1. **Two of the four states can never be produced.** `wizard.rs:17-23`
   `state_from_authenticated_bridge(connected)` returns only `Connected` or `UnreachableRetrying`.
   `DaemonState::UnitMissing` and `UnitInactive` (`wizard.rs:10-15`) have no producer.
   `wizard_controller.rs:12-36` maps them to names and detail text that production never shows.
   Only the keyboard probe reaches them, by setting `wizard.state = "unitInactive"` directly
   (`tests/probes/status_pages_probe.qml:312`).
2. **The button shows in a state it cannot fix.** `qml/OnboardingPage.qml:143-150` shows "Start
   daemon" on `unitInactive` **or `unreachableRetrying`**, and `unreachableRetrying` is the only
   failure state that exists. It means "the GUI has no authenticated bridge connection"
   (`wizard_controller.rs:100-109`, `bridge_runtime::handles().is_connected()`). Starting
   `opensnitch.service` (the daemon) does not start the bridge, which is socket-activated
   (`packaging/system/snitchwatch-system-bridge-gui.socket`). It also does not fix the documented
   causes:
   - the socket is missing (`docs/packaging/system-bridge-integration.md:158-195`, "Missing
     socket, and console recovery"; the recovery starts both sockets *before* the daemon);
   - the user is not in `snitchwatch-ui`, or has not logged in again since being added
     (`system-bridge-integration.md:20-21`, `:278`; `packaging/system/snitchwatch-system-bridge-gui.socket:9`);
   - the bridge is crash-looping (`docs/RUNBOOK.md`, "Crash-looping bridge" row).
3. **It cannot work in the shipped GUI.** The only shipped GUI is the system Flatpak
   (`system-bridge-integration.md:252-258`). Its `finish-args`
   (`packaging/flatpak/org.snitchwatch.Snitchwatch.system.yml:54-91`) grant no
   `--system-talk-name=org.freedesktop.systemd1` and no `--talk-name=org.freedesktop.Flatpak`
   (for `flatpak-spawn --host`). A grep for `system-talk|systemd1|flatpak-spawn` in the manifest
   finds nothing. So the sandboxed `systemctl` either does not exist (`which` fails) or cannot
   reach host systemd. UNVERIFIED: which of the two `org.kde.Platform` 6.11 does; the outcome is
   an error string either way. Native launches (`SNITCHWATCH_SYSTEM_BRIDGE=1 snitchwatch-kirigami`)
   would reach polkit, but they would start the wrong unit (point 2).
4. **The `unitMissing` hint points at a retired doc.** `OnboardingPage.qml:119-121` sends the
   user to `docs/packaging/rpm-ostree-layering.md` "to layer the OpenSnitch daemon". That page
   now says the path is retired (`rpm-ostree-layering.md:1-6`). The text is dead anyway (point 1).

### Decision: remove the action, do not retarget it

Retargeting has no correct target. The GUI has only one signal: "the authenticated bridge
connection is down". The fix for that depends on host state the sandbox cannot see (socket,
group, crash loop, daemon), and each fix needs root. A button that starts the right unit would
need host systemd access (`--system-talk-name=org.freedesktop.systemd1`). That widens the
sandbox's privilege surface, which settled decision 3 (`CLAUDE.md`) keeps narrow. Removing the
action is honest and adds no permission.

User-visible behaviour after the change:
- The page has two states: `connected` (page hidden, `main.qml:224-229`) and
  `unreachableRetrying`.
- Title: "Waiting for the bridge" (unchanged). Auto-retry with capped backoff (unchanged,
  `OnboardingPage.qml:35-48`). Buttons: **Retry** and **Continue anyway** only.
- Detail (`state_detail(UnreachableRetrying)`): "Can't reach the Snitchwatch system bridge. It
  runs as a system service; this app can't start it. Check that your account is in the
  `snitchwatch-ui` group (log out and back in after adding it) and that the bridge sockets are
  running. The client retries automatically."
- Guidance block (replaces the layering hint, visible on `unreachableRetrying`): "Setup and
  recovery steps: docs/packaging/system-bridge-integration.md ("Missing socket, and console
  recovery"). After connecting, Daemon Health shows the OpenSnitch daemon's status." Plain text,
  `Text.WordWrap`, as the honest-UI guards require.
- Keep the `DaemonState` enum with two variants rather than a bare `bool`: it keeps the QML
  contract (`state` string) and the controller's mapping unchanged.

## #386: move bridge tests from DevTcp to the per-user Unix gRPC socket

### What differs between `DevTcp` and `UserUnix` (verified)

- **Trust: identical.** Every production gate asks `peer_is_trusted_daemon()`, which is
  `self == Unix` (`snitchwatch-bridge/src/daemon_commands.rs:112-115`). It is false for both `Tcp`
  and `UnixUser`. Call sites:
  - `daemon_commands.rs:334,645,672,702` (fan-out and stream failure);
  - `blocklists/leftover.rs:73`;
  - `cache/rule_hits_handle.rs:248` (counters);
  - `bridge-cli/src/rules_import.rs:233`;
  - `rule_commands/gates.rs:79`.

  No production code compares `== DaemonTransport::Tcp`. The only production mention is the
  mapping `bridge-cli/src/lib.rs:265`; the other is the `UiService::new` default at
  `grpc_server.rs:156`, which `with_daemon_transport` overrides. Fan-out, untrusted counters, the
  leftover branch and the import/rule refusals therefore behave the same on `UnixUser`
  (`daemon_commands.rs:57-58`).
- **Connection identity: differs.** `ConnKey = Option<SocketAddr>` (`daemon_commands.rs:79-84`)
  comes from `request.remote_addr()` (`grpc_server.rs:287,534,641`). On TCP each mock has its own
  key. On a Unix socket tonic gives no remote address, so **every per-user peer shares `None`**.
  `OwnerUnixIncoming` yields plain `UnixStream`s (`activation.rs:154-191`); UNVERIFIED by a run,
  but the module doc says the same. Consequence: the version gate
  (`daemon_commands/version_gate.rs:27-44`), "a second TCP peer pinging another version can't move
  a known one", does not separate two same-uid peers on `UnixUser`. Any test that runs **two
  mocks at once** and relies on distinct peers changes meaning.
  - A grep of the 34 files for second/another/impostor/forged peers, `ping.*version` and
    `DaemonTransport::` found none. The two-peer version tests live in `snitchwatch-bridge` unit
    tests with `DaemonTransport::Tcp` directly (`version_gate.rs:116,140,164`), which #386 does
    not touch.
  - **Security note (new issue, not a blocker):** on the per-user socket, a same-uid process can
    move the recorded daemon version. Dev/test only: nothing ships the per-user flavour (#35
    learning). The socket also admits the owner uid by design (`activation.rs:150-161`). File it
    for the opus reviewer to rate.
- Other differences: the socket path length limit (`sun_path` is 108 bytes; tempdir paths are
  short, but assert it in the helper) and `bind_user_socket`'s 0700-dir rule
  (`user_socket.rs:14-60`).

### Helper design

`crates/snitchwatch-bridge-cli/src/config.rs`, next to `dev_tcp_for_tests` (`:85-91`):

```rust
/// The per-user Unix gRPC socket under `dir` (a fresh tempdir): the shape
/// `from_env` resolves for XDG_RUNTIME_DIR=dir, built without reading the
/// environment. Test support only.
#[doc(hidden)]
pub fn user_unix_for_tests(dir: &Path) -> Self
// grpc: dir/snitchwatch-grpc/opensnitchd.sock ; ws: dir/snitchwatch/bridge.sock
```

- It takes a **directory**, not the WS socket path. Restart tests start two bridges
  (`rule_hits_restart_tests.rs:74` uses `bridge{n}.sock`), so each bridge gets its own subdir:
  `user_unix_for_tests(&dir.join(format!("b{n}")))`. The paths match
