# #329 items 3 and 4: sweep walks the subtree, scanner gets its own session

Issue #329 (tower security reviews of 32eca9a7..850c0cc9, 0 CRITICAL/HIGH). Items 1 and 2 are
already on main (#336 `3131f889`, #337 `c9807ebe`). The owner asked for items 3 and 4
(2026-11-15). Two independent PRs so each reviews and reverts alone.

## PR 3: `fix/329-sweep-subtree` (crates/scanner-privileged/src/containment.rs)

Today `live_members` reads `/proc/<pid>/stat` for EVERY process under one 2 s deadline and
`read_stat_with_start(pid)?` / `has_other_tasks(pid)?` abort the whole pass on any
non-"vanished" per-pid error (EMFILE, EIO), so one unreadable pid discards what the pass found
(the caller records a failed sweep).

Design (decided here, TDD, no change to what counts as live or to the kill rule):
1. **Per-pid errors do not discard the pass.** A non-vanished error on one pid is skipped, the
   pass is marked incomplete, and the pass still returns every live descendant it did find so the
   caller kills them. An incomplete pass never counts toward the "two consecutive empty passes"
   completion rule (fail closed: the sweep stays incomplete and exit 3 semantics are unchanged).
   `live_members` returns a small struct (live members, complete flag, first error) instead of
   `Option<Vec<_>>`; keep `live_descendants` (test helper) working.
2. **Walk only the subtree.** Starting at `root`, read `/proc/<pid>/task/<tid>/children` for every
   task of every visited pid (a thread's children are listed under that thread), read the stat of
   the children found, and recurse. Cost is proportional to the subtree, not to `/proc`. If the
   `children` file does not exist (kernel without CONFIG_PROC_CHILDREN: ENOENT on the root's
   first task), fall back to today's full `/proc` scan. Keep the deadline check inside the walk.
   A child forked after its parent's `children` was read is caught by the next pass (the sweep
   already requires two consecutive empty passes); document that in the doc comment.
3. Tests first: (a) one unreadable pid among live descendants does not hide the descendants
   (inject the per-pid reader or use the existing fakes; do not depend on real EMFILE), the pass
   reports incomplete, and the caller still kills the found ones; (b) the subtree walk finds a
   deep tree plus a multi-threaded process whose children hang off a non-leader thread; (c) an
   unrelated process is never visited/killed; (d) the ENOENT fallback path; (e) the existing
   `completion_needs_two_consecutive_empty_passes` and `sweep_kills_descendants_but_spares_unrelated_processes`
   still pass unchanged.

## PR 4: `fix/329-setsid` (scanner-privileged/src/main.rs, scanner-broker/src/lib.rs)

`start_privileged_watchdog_after` does `setpgid(0, 0)`; a same-session process can then
`setpgid` itself into the scanner's group and become a `killpg` target (LOW). `setsid()` fails
with EPERM for a process that is already a group leader, and the broker spawns the scanner
through `pkexec` with `.process_group(0)` (scanner-broker/src/lib.rs:97-105), so the scanner IS
already a leader when it starts. So:
1. **Scanner:** try `setsid()` first; on EPERM fall back to the existing rule (`getpgrp() == pid`
   else error), unchanged. Covers direct and other launchers.
2. **Broker:** replace `.process_group(0)` with a `pre_exec` that calls `setsid()` (async-signal-safe;
   `// SAFETY:` comment; the child becomes session AND group leader, so `pgid == pid` still holds
   for the broker's own `killpg`). Separate commit so it can be reverted alone.
3. **Known unverified risk, to flag in the PR and to the tower:** pkexec under a new session with
   no controlling tty. polkit identifies the subject by pid/start time and the logind session, not
   by SID, so this should be fine, but it cannot be verified in CI. The tower must run one real
   scan on a VM/host before this goes in an image.
4. Tests first: scanner-side unit test for the setsid/EPERM decision (extract a small pure
   function over the two syscall results); broker test (fake pkexec exists in
   `scanner-broker` tests) that the spawned child is a session leader (`getsid(pid) == pid`) and
   its pgid equals its pid.
